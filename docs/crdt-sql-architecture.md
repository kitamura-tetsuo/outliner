# CRDT and SQL: division of responsibilities

Status: accepted (rationale for what is implemented) + planned (the write-back
relation section, not yet implemented).

This document records *why* documents are CRDT-centric while tabular data is
SQL-centric, and how a surface that has to show both — a calendar of tasks — is
meant to be built without reintroducing a second source of truth.

Until now this rationale lived only in issue #3920 and in the header comments of
`client/src/services/yjstable/*.ts`.

## 1. The principle

**Yjs is the single source of truth. SQL is a derived, read-only-by-construction
computation layer.**

The split is not "documents are stored in a CRDT, data is stored in a database".
Both are stored in Yjs. What differs is the direction of writes:

- Users, and the server scheduler, always write to Yjs.
- PGlite is materialized *from* Yjs, one-way, and may be dropped and rebuilt at
  any time (`DROP SCHEMA CASCADE`).
- Nothing is ever persisted only in PGlite.

Where this is stated in the codebase:

- `client/src/services/yjstable/tableSyncAdapter.ts` — "One-way Yjs → PGlite
  synchronization. Data Storage (Y.Map of records) is the source of truth."
- `client/src/services/yjstable/tableEngine.ts` — a table is materialized
  exactly once per project; entries no longer reachable from a live session are
  swept, so a query can never read stale rows.
- `server/src/scheduler/` — the scheduler writes only Yjs. Its SQLite
  `schedule_index` is an index derived from documents in the Hocuspocus
  `onStoreDocument` hook; documents are never scanned.

## 2. Why the responsibilities are split this way

1. **Merge semantics differ.** A document's defining case is two people editing
   the same sentence, which needs character-level CRDT. Tabular data merges per
   cell, which a nested `Y.Map` (`recordId → column → value`) already gives.
   Neither structure can express `SUM` / `JOIN` / `GROUP BY`.

2. **Querying is what CRDTs are bad at.** Implementing aggregation over CRDT
   structures means inventing a rule DSL. The project's standing policy
   (`schemaIntrospection.ts`) is that SQL is *never parsed by hand — the accepted
   grammar is exactly what Postgres accepts*. Schedule rules follow the same
   policy: they are SQL run by a real engine, which is also more LLM-friendly.

3. **Making SQL the truth would break everything the CRDT buys.** Offline
   editing (FTR-7fa5a073), undo, per-table undo scopes, and embedding the same
   table in several places all depend on Yjs being authoritative.

4. **Cost.** No persistent server-side Postgres, no Cloud Scheduler. A one-minute
   tick inside the existing Hocuspocus process, running user SQL in a worker
   thread against a throwaway schema.

## 3. The problem this leaves: surfaces that span both

A calendar of tasks draws from two places:

1. tasks typed into the outliner while writing;
2. rows generated by schedule rules (e.g. `routine_occurrences`).

The naive options are both bad. A calendar that mixes item-derived and
table-derived entries makes the *user* reason about provenance. A calendar that
shows only SQL rows silently drops half the user's tasks.

What actually confuses users is not the data source — it is inconsistent
affordances: two adjacent entries where only one can be dragged.

## 4. Decision: items project into SQL as a write-back-capable relation

Outline items are materialized into PGlite as a relation like any table, and
that relation accepts writes, which are applied to the item's Y.Map.

- **Reads are uniformly SQL.** The calendar is one query. The UI never branches
  on provenance for display.
- **Writes are dispatched by provenance.** Table rows → the table's Data Storage
  `Y.Map`; item rows → the item's node value. Nobody writes to PGlite, so §1 is
  preserved.

### 4.1 Schedule attributes are structured fields, not text

Dates must **not** be parsed out of item text. Dragging in the calendar would
then rewrite the item's body — using text as a datastore, which is the weakness
this project exists to avoid.

Instead the item's node value `Y.Map` carries typed fields (`due`, `done`,
…), alongside the existing typed slots (`componentType`, `aliasTargetId`,
`templatePageId` — see `shared/src/app-schema.ts`). The text stays the title.
The user-facing rule becomes: *give an item a date and it appears on the
calendar*.

### 4.2 Projection scope

Only items that carry the structured field are projected. This keeps the
relation sparse (projecting every item of every page does not scale) and matches
the user-facing rule above.

Synchronization must be incremental: items live across the page structure
(`YTree`), not in a single subdoc's Data Storage, so the projection is
maintained by diffed upserts from `observeDeep`, never by full rebuild. Write-back
carries a transaction origin so the adapter ignores its own echo, as
`ADAPTER_ORIGIN` already does.

### 4.3 Write capabilities of the items relation

The items relation is deliberately asymmetric with real tables, because the
inverse mapping is asymmetric:

| Operation | Behavior |
| --- | --- |
| `UPDATE` | Writes the mapped field of the item's node value. This is the drag-to-reschedule path. |
| `INSERT` | Allowed. The destination (page and parent) is **chosen explicitly at each creation**, with previously chosen destinations offered as history. There is no implicit inbox. |
| `DELETE` | Prompts each time: delete the item itself, or only clear its date so it leaves the calendar. Never silently destructive. |

Capabilities are a property of the relation, expressed explicitly, in the same
spirit as the editability rules in `queryAnalysis.ts` (a result is read-only
without an `id` column, or when it uses JOIN / aggregation / grouping).

### 4.4 Row identity across the projection

A calendar query that unions items with generated rows currently trips the
read-only rules above. What is needed is not "make items read-only" but a notion
of row identity that survives the projection: a `source_kind` + `source_id` pair
carried in the result, with `analyzeQueryEditability` generalized to keep a
result editable while that pair is preserved. The same generalization then
serves any union of several tables.

### 4.5 Reserved SQL name

The items relation is system-defined; no user authors its `CREATE TABLE`. Its
SQL name is reserved and added to the reserved-word list in `sqlNames.ts`, so a
user table can never claim it. No migration is required — no existing project
uses the name.

### 4.6 Undo

There is one undo/redo stack, and it delegates.

Today there are already two scopes: the outline's `orderedTree` manager
(`client/src/stores/store.svelte.ts`) and a per-table manager
(`client/src/services/yjstable/tableDocs.ts`). A single global stack records
which scope each operation was applied to, and undo pops that stack and calls
undo on the corresponding scope.

The hazard to respect: each `Y.UndoManager` keeps its own internal stack, so the
global stack must be the **only** entry point. Any path that calls undo directly
on a scope desynchronizes the two.

## 5. Implementation shape

Generalize the port that `TableSyncAdapter` already takes
(`TableRegistryPort`) into a relation provider: `materialize()`,
`applyWrite(rowId, column, value)`, and declared capabilities. Real tables
implement it as `rowId → Data Storage Y.Map key`; items implement it as
`item key → node value field`.

This keeps the inverse mapping closed per relation, and keeps the invariant that
no component writes to PGlite.

## 6. What must not be done

- Do not persist the item projection into any table's Data Storage. It is a
  virtual relation, rebuilt on the client like everything else in PGlite. Storing
  it creates a second truth.
- Do not make PGlite authoritative for any field, on client or server.
- Do not encode schedule attributes in item text.
