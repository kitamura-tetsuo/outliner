# ChatGPT and Codex remote MCP operator guide

Outliner exposes a Streamable HTTP MCP server and an OAuth 2.0 authorization-code + PKCE bridge. A connection may be **read-only** (`outliner.read`) or **read/write** (`outliner.read outliner.write`). The connected identity is the Firebase `uid` from Google-backed Firebase Auth, and every tool uses the existing project authorization path. Enabling diagnostics never implicitly enables mutation.

## Public routes and environment

Publish one HTTPS origin, referred to below as `https://outliner.example.com`:

- MCP: `/mcp`
- authorization and token/refresh: `/oauth/authorize`, `/oauth/token`
- revocation and dynamic registration: `/oauth/revoke`, `/oauth/register`
- OAuth/OIDC discovery: `/.well-known/oauth-authorization-server`, `/.well-known/openid-configuration`
- MCP protected-resource discovery: `/.well-known/oauth-protected-resource/mcp` (the un-suffixed path is an alias)

The proxy must preserve HTTPS host/protocol forwarding headers and route `/mcp`, `/oauth/*`, and `/.well-known/*` to the same process. Set `OAUTH_ISSUER` to the exact public origin, set a long stable `OAUTH_ACCESS_TOKEN_SECRET` shared by every replica, and provide the same `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, and `VITE_FIREBASE_APP_ID` used by the web client. Firebase Admin credentials remain required. `OAUTH_STATIC_CLIENTS` is optional because PKCE dynamic registration is supported.

Do not commit secrets. Keep the short access-token lifetime and persistent refresh-token store. Refresh tokens retain their original scope and cannot upgrade a read-only grant. The consent page states whether access is read-only or read/write; request `outliner.write` only for a workflow that will mutate data. Google is the only supported sign-in provider.

Clients that assumed exactly seven read-only tools must migrate to capability discovery: call `tools/list`, select by tool name, and honor each tool's `readOnlyHint` and `destructiveHint`. Do not reject additional tools or infer permissions from list length. A read-only token can discover the catalog but calls to write tools return `forbidden`.

`create_table` creates one standalone, empty, project-owned Table and nothing else: no records, Grid, Page, or placement. Insert records with `write_relation` and add a Grid with `create_grid` using the returned `sqlName`/`tableId`. The input fields are exactly `projectId`, `name` (an empty string stays empty), `schemaSql`, `operationId`, and optional `dryRun`; any other field is rejected with `invalid_argument`. The declaration is validated by executing it in an isolated database; its catalog name becomes `sqlName`, which must not be `outline_items` or another Table's SQL name in the project (`validation_failed` with `reason: "relation_name_unavailable"`). A dry run returns the resolved metadata without `tableId` or `revision` and never creates, reserves, or consumes anything, including its operation ID. Retry a lost or failed response with the same operation ID; use a new one for different input. Outcomes are retained for five minutes after the creation settles, in the serving process only (not across a restart); a replay returns the original creation with `replayed: true`, not the Table's current state. `internal_failure` with `creationOutcome: "unknown"` and `applied: null` means publication was attempted but not confirmed: the response carries the candidate `tableId`, and a same-ID retry within the window returns the same uncertain result without creating again. Refusals before publication report `creationOutcome: "not_created"` and may be retried with the same ID. Project access is checked before replay lookup, before publication, and before disclosing an awaited result; a denied caller learns nothing about a retained outcome.

`create_grid` appends one Grid placement to an existing top-level Page and creates its project-owned definition atomically. A dry run performs the same validation without modifying project state or consuming the operation ID; its revision predicts the applied query revision. Read the returned IDs with `get_grid`, `trace_grid`, and `get_item`. No `expectedRevision` is required for this append operation. Retries reuse the original IDs within the existing in-memory replay cache lifetime (five minutes); use a new operation ID for a different logical creation. Replay is not restart-persistent and does not compare payloads. Every call checks current project access before replay lookup, immediately before publication, and before returning an awaited result. Successful apply/replay audit entries identify `grid:<gridId>` and omit query/row payloads.

## Grid presentation editing (`update_grid_presentation`)

`get_grid` returns two independent revisions: `revision` covers only the saved SQL query text (consumed by `update_grid_query`), while `presentationRevision` (`grid-presentation-v1:<hash>`) covers the saved presentation snapshot (`presentation`: display `name`, stored `columnOrder`, per-column `components`, `showAddRowButton`, `confirmRowDelete`). A label-only edit moves `presentationRevision` and leaves `revision` unchanged; passing the query revision as `expectedPresentationRevision` fails.

A saved presentation snapshot is configuration evidence, not proof that the query executed or that a particular column currently renders. Saved settings may name exact result names absent from the current query: dormant names stay stored but render nothing until the query projects them again. The normal browser renderer consumes the same saved state after synchronization/reload: a nonempty `label` override replaces the header text (clearing restores the result name), DOM column identity and edit targets stay bound to the unchanged result names, visible order is present saved-order names followed by remaining result names in result order filtered by `shown` (empty order restores result order), explicit `text`/`number`/`checkbox`/`select`/`date` types select the matching cell renderer (`null` restores automatic selection), `showAddRowButton` controls the add-row button, and `confirmRowDelete` controls deletion confirmation. Neither flag is an authorization rule.

Target columns by exact SQL result name, never by displayed label or JSON/Yjs path. `changes` accepts only `name` (string, empty allowed), `columnOrder` (0-100 unique nonblank strings), `components` (1-100 exact result-name keys, each with one or more of `label` string|null, `type` text/number/checkbox/select/date|null, `shown` boolean), `showAddRowButton` and `confirmRowDelete` (booleans); unknown keys at any level, `hidden`, and any query/schema/record/source/placement input are rejected as a whole. Resets and defaults: `label` is trimmed and `null`/trimmed-empty clears it; `null` type restores automatic selection; `shown: true` clears `hidden` and `shown: false` sets it; `showAddRowButton: true` and `confirmRowDelete: false` restore their defaults; the supplied order replaces only the order preference while omitted fields (including other keys and per-column maps) survive untouched.

Read the current `presentationRevision` from `get_grid` immediately before writing and pass it as `expectedPresentationRevision`; a concurrent presentation (or query/source-context) change returns `stale_revision` with `currentPresentationRevision` and writes nothing — re-read, reconcile, and retry as a new intent. Table data/schema, Page/placement, and other-Grid edits do not invalidate the token. A dry run (`dryRun: true`) previews with detached `candidatePresentation` plus `wouldChange` and persists nothing (not even its operation ID); an accepted no-op apply returns `applied: false` with equal prior/resulting revisions and no document/history update. Retry a lost response with the same `operationId`; use a new one for different input. Outcomes are retained for five minutes after settlement in the serving process only (never across a restart); a replay returns the original outcome with `replayed: true`, never current state, and never overwrites a later edit or recreates a deleted Grid. Reusing a retained operation ID with different `changes`/`expectedPresentationRevision` is rejected with `invalid_argument` (`operation_id_reused`).

Japanese-label workflow (edits presentation only, never SQL):

1. Read: `get_grid` with `projectId`/`gridId`; record `presentationRevision` (for example `P0`) and the exact result names (for example `due_date`, `done`).
2. Preview: `update_grid_presentation` with `expectedPresentationRevision: P0`, `changes: {"components": {"due_date": {"label": "期限"}, "done": {"label": "完了"}}}`, a fresh `operationId`, and `dryRun: true`; confirm `wouldChange` and re-read to prove nothing changed.
3. Apply: repeat with `dryRun: false` and the same `operationId`; record the new `presentationRevision` (`P1`).
4. Re-read: `get_grid` shows `presentationRevision: P1`, Japanese headers in the normal Grid, unchanged query text, and unchanged record IDs/values.

## Limits and result interpretation

- Subtrees: depth at most 10 and at most 500 nodes. Search: at most 100 results.
- Table record pages: default 25, maximum 100. Continue with the opaque cursor; do not parse or synthesize it.
- `update_table_records.changes`: at most 100 records and 64 KiB per call. Split a larger rewrite (for example populating a new ordering column) into several bounded calls, each re-reading `get_table`'s revision first.
- SQL, Grid validation, and trace reads are bounded. Respect `truncated`, the effective limit, continuation metadata where present, and stage-level row counts; a returned page is not proof that no more data exists.
- Queries must be one read-only `SELECT`/`WITH` statement. Writes are structured operations, not arbitrary SQL.
- Query and schema text, write payloads/batches, IDs, URLs, and cursors are validated and size-limited. Split legitimate large work into bounded calls; never retry a `size_limit` unchanged.
- Ordering without SQL `ORDER BY` is incidental, not a stable guarantee. Reserved identifiers must be quoted, for example `ORDER BY "order"`.
- `update_table_records` writes record values only; it never reorders a Grid's displayed rows. Use `update_grid_query`/`set_view_query` with an explicit `ORDER BY` for display order.

## Safe diagnostic-to-repair workflow

1. Obtain a read-only grant first and resolve the canonical `/{project}/-/tables/{tableId}` URL.
2. Use `get_table` with bounded records, then `trace_grid`. Inspect every trace stage; an execution error or `incidental-source-order` means ordering has not been proven.
3. Use `validate_grid_query` with the corrected SELECT, such as `SELECT id, "order" FROM tasks ORDER BY "order"`. Validation is always non-mutating.
4. Reauthorize with `outliner.write` only after mutation is approved. Read the current target revision immediately before changing it.
5. For a Grid repair, call `update_grid_query` with `dryRun:true`, `expectedRevision`, and a unique stable `operationId`. It executes the exact query without rewriting it and rejects dependencies that cannot be safely materialized. Re-read the target to prove the dry run made no change.
6. Apply the identical operation with `dryRun:false`, the same expected revision, and the operation ID. Keep the operation ID for transport retries; changing it creates a distinct operation.
7. Re-read/trace and verify both the new revision and semantic outcome (for example row identities appear in the requested SQL order).

A concurrent update returns `stale_revision` and the current revision. Do not blindly retry: re-read, reconcile the proposal, dry-run it again, and use a new operation ID for the revised intent. Repeating an already-applied operation ID returns the recorded result with `replayed:true` and does not duplicate the mutation. Validation occurs before persistence; failed operations do not partially apply.

## Structured errors

Tool-level failures that reach Outliner's handler set `isError:true`; parse their JSON text rather than matching prose. It contains `code`, a safe `error`, and `requestId`, with bounded diagnostic fields where useful. The MCP SDK may reject an input that does not match the advertised JSON schema before the handler runs; that protocol-level response is plain `Input validation error` text rather than Outliner's structured JSON contract. Treat it as `invalid_argument`, correct the call from `tools/list`'s current input schema, and do not retry it unchanged.

| Code                                              | Operator action                                                                                                                                                       |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid_argument`                                | Correct malformed IDs, canonical URL, cursor, SQL, or operation shape.                                                                                                |
| `forbidden`                                       | Verify project membership and that a write call has an approved `outliner.write` grant. Do not disclose whether an inaccessible entity exists.                        |
| `not_found` / resolution-specific not-found codes | Re-resolve authorized URLs and IDs.                                                                                                                                   |
| `stale_revision`                                  | Re-read, reconcile, revalidate, and retry as a new intent.                                                                                                            |
| `validation_failed`                               | Correct schema/query/write compatibility; no mutation was applied.                                                                                                    |
| `destructive_confirmation_required`               | Review the returned migration diff; retry the identical `update_table_schema` call with `acknowledgeDestructive: true` only if the column removal/retype is intended. |
| `size_limit`                                      | Reduce the bounded read or split the write.                                                                                                                           |
| `internal_failure`                                | Correlate the safe `requestId` with server logs; do not expose internal log details to the client.                                                                    |

## Audit and privacy

Every `create_table`, `create_grid`, `update_schedule_rule`, `update_table_schedule_sql`, `write_relation`, `set_view_query`, `update_grid_query`, `update_grid_presentation`, `update_table_schema`, and `update_table_records` attempt that passes the MCP SDK's input-schema check—including dry runs, handler validation failures, scope failures, and replays—writes an `mcp_audit` JSONL record. `update_grid_presentation` entries carry `entity: "grid:<gridId>"` with prior/new presentation revisions, `applied` (`null` only for an unknown outcome), and `replayed`. Table tool entries carry `entity: "table:<tableId>"`. For `create_table` and `create_grid`, schema-invalid calls also return structured `invalid_argument` errors and write a mutation audit record; other tools retain their existing schema-validation behavior. Retain transport/security logs if protocol-level rejection accounting is required. `create_table` records identify `table:<tableId>` from the result (never from input) and add `creationOutcome`; an unknown publication is recorded with `applied: null`, and a result withheld from a caller whose access was revoked after an authorized creation still records that effect. Audit entries contain the request ID, a one-way uid fingerprint, tool, project/entity identifiers, operation ID, dry-run/applied/replayed state, outcome, and prior/new revisions. They deliberately exclude bearer/refresh tokens, raw uid, authorization headers, query text, row values, and full payloads. Restrict and rotate the log like other security audit data. Use request IDs for correlation and never paste tokens into issue reports.

## Production connector smoke test

Prepare authorized project A and inaccessible project B. In A, create a Table with an integer column named `order`, records stored out of order, and a Grid whose unquoted query fails. Record only origin, date, uid fingerprint, operation ID, revisions, and pass/fail.

1. Verify OAuth/OIDC/protected-resource discovery, PKCE connection, Google-only consent, requested scope text, token refresh, and revocation.
2. With `outliner.read` only, list tools and verify annotations. Run every read/diagnostic tool against B and confirm an isolation failure with no title, IDs, counts, schema, or rows. Confirm both write tools return `forbidden`.
3. Against A, resolve its canonical Table URL, inspect bounded schema/records, and trace the broken Grid. Confirm malformed IDs/URLs, oversized limits, and non-SELECT SQL fail safely; confirm truncation metadata at a low limit.
4. Validate the corrected query containing `ORDER BY "order"`; confirm the saved query and revision did not change.
5. Reconnect with explicitly approved `outliner.write`. Dry-run `set_view_query` with the expected revision and operation ID, then re-read to prove no mutation.
6. Apply it, retry the same operation ID to confirm `replayed:true`, and trace the Grid to verify SQL ordering. Attempt the old revision to confirm `stale_revision` without rollback damage.
7. Exercise an invalid structured write and an oversized write; verify validation failure/no partial mutation. Review audit and error logs for identity/revision metadata and absence of tokens, query text, and sensitive row payloads.

The live ChatGPT/Codex connector run is a release smoke test; deterministic service, HTTP MCP, OAuth, integration, and production-protocol tests remain the regression suite.

## Schedule diagnostics and repair

Schedule list URLs use `/{project}/-/schedules`; detail URLs use `/{project}/-/schedules/{ruleId}`. `list_schedules` pages at most 100 stable-ID rules and can filter a Table reference as `write-target`, `sql-reference`, or `any`. A Table is only referenced by a Schedule—it does not own the project-level rule. `get_table.scheduleReferences` is bounded to 25 entries; continue with `list_schedules` for the authoritative paged set. Each write-target entry also embeds that Schedule's `sql`, `rrule`, `dtstart`, `timezone`, `enabled`, and `revision`, so a client can read a Table's scheduled SQL from `get_table` alone.

`get_schedule.stored` is the exact persisted definition: SQL, RRULE, local-wall-clock DTSTART, IANA timezone, enabled/catch-up flags, and fields written by the scheduler. `derived` contains validator output, dependency evidence, authoritative Table revisions, and at most five computed instants. A disabled or completed rule has no next instants. For active rules, catch-up permits occurrences after the persisted last run, while non-catch-up output starts after the current instant. `execution-status` repeats only fields actually persisted; an absent field is never invented.

`validate_schedule_rule` runs field validators, loads real dependency schemas and records into isolated scratch SQL state, sets the explicit `job.occurrence`, executes the candidate, applies target constraints, and returns at most 100 candidate rows. Scratch execution never writes Yjs, records, revisions, scheduler indexes, last-run fields, undo history, or audit history. Deterministic-ID evidence is conservative: fixed IDs and IDs derived from `job.occurrence` are retry-safe; random UUIDs, sequences, omitted IDs, and unproved expressions are not. `update_schedule_rule` requires `outliner.write` and `expectedRevision`, uses that same preview path, applies only named fields atomically, and never enables or runs a rule unless explicitly requested. `operationId` makes an applied retry replay-safe. Running now remains the separate Schedule API and is never implied by an MCP update.

### Table → Schedule → recurring row example

1. Resolve `/{project}/-/tables/{tableId}`, call `get_table`, then page `list_schedules` with that Table and `write-target`.
2. Read the rule. Compare exact stored SQL and `lastRunError` with the target schema. For a numeric column named `order`, unquoted `order` is SQL syntax rather than the column; use `"order"`.
3. Preview the corrected candidate with an explicit occurrence and a small `resultLimit`. Confirm candidate rows and deterministic IDs, then reread the Table and Schedule to prove their records, revisions, enabled state, and last-run state did not change.
4. After explicit write approval, call `update_schedule_rule` with only `sql`, the preview's Schedule revision, and an operation ID. Reread and verify the new revision. No task exists until the scheduler fires or a separately authorized run-now request executes.
5. Audit records contain fingerprints, IDs, outcomes, and revisions but redact SQL, row values, credentials, and raw user identity. A stale revision must be reread and revalidated rather than overwritten.

When the correction is scoped to one Table's own SQL, `update_table_schedule_sql` collapses steps 1, 2, and 4 above into a Table-centric call: read the SQL and revision straight from `get_table.scheduleReferences`, then call `update_table_schedule_sql` with `projectId`, `tableId`, the corrected `sql`, and that same expected revision. It fails explicitly—rather than guessing—when the Table has no write-target Schedule or more than one; use `update_schedule_rule` with an explicit `ruleId` in that ambiguous case.
